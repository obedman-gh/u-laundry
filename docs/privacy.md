# Privasi pelanggan dan tracking — hari 11

## Tindakan — Hasil

- Data pelanggan minimum — hanya nama wajib (maksimal 100 karakter). Kontak opsional dinormalisasi; alamat maksimal 500 dan catatan layanan maksimal 1.000 karakter, keduanya opsional dan dapat dikosongkan saat edit. Tidak meminta NIK, tanggal lahir, email, lokasi presisi, atau data sensitif. Nama/kontak tidak unik: keluarga dapat berbagi nomor; tidak ada merge otomatis.
- Customer management internal — owner/admin/cashier aktif dapat membuat, mencari nama/nomor, membaca, dan mengedit dengan expected version; cookie dan CSRF berlaku. Daftar hanya mengembalikan ID/nama/kontak. Alamat/catatan hanya pada detail yang dipilih; pencarian tidak menelusuri catatan/alamat. Query maksimal 100 karakter, wildcard dianggap teks literal, pagination maksimal 100. Riwayat difilter customer ID dan tetap memerlukan izin baca order.
- Snapshot historis — edit profil tidak mengubah order/struk yang sudah diterima. Schema existing menyimpan snapshot nama/kontak/catatan pada order; alamat baru hanya disimpan di profil, tidak disalin ke order. Penghapusan/anonimisasi snapshot lama belum diimplementasikan karena berkaitan dengan histori transaksi.
- Capability tracking — generator existing crypto/rand 32 byte (256 bit), Base64URL canonical tanpa padding (43 karakter), dipertahankan. ID order dan kode tampilan tidak dapat dipakai untuk lookup publik. Database hanya menyimpan SHA-256 token, panjang hash 32 byte, UNIQUE(token_hash) dan satu token aktif per order (PK order_id). Token mentah hanya muncul pada respons privat create/rotate, tidak dapat diambil kembali dari database.
- Projection publik — tepat empat field: tracking_code (12 digit hex dari hash, hanya referensi tampilan), status, estimated_ready_at, message layanan terkontrol dari status. Kode tampilan bukan credential dan tidak dijamin unik; uniqueness yang melindungi capability ada pada hash penuh. Tidak ada order/customer ID, nama, nomor, alamat, catatan, layanan/item, harga, pembayaran, ledger, actor, ready_at atau collected_at.
- Masa berlaku — token baru kedaluwarsa 90 × 24 jam sejak penerbitan. Lookup menolak saat waktu server >= expires_at; tidak ada perpanjangan karena dibaca atau karena status berubah. Migration 000007 memberi token existing grace period 90 hari sejak migration, tanpa mengubah hash. Setelah kedaluwarsa, staf dapat menerbitkan pengganti.
- Rotasi sadar oleh staf — POST privat /api/pesanan/{id}/tracking dengan version order terkini mengganti token dan menaikkan version. Lock order dan expected version menolak rotasi bersamaan/stale. Token lama langsung tidak berlaku untuk lookup berikutnya setelah commit; respons yang sudah dikirim tidak dapat ditarik kembali. Collision, error generator/storage/audit/commit tidak menghasilkan token sukses; perubahan rollback. Event order_tracking_rotated hanya menyimpan actor/order ID, aksi, dan waktu.
- Struk — /api/pesanan/{id}/struk tetap internal, memerlukan sesi dan izin ReadOrders pada use case; HTML memakai escaping dan no-store. Tidak menyediakan struk publik karena kebutuhan bisnisnya belum ada. Token tracking tidak memberi izin mengakses struk internal, riwayat, atau endpoint internal lainnya.
- Kegagalan publik generik — token malformed, tidak dikenal, expired, atau sudah dirotasi mendapat 404 not_found dengan pesan yang sama. Ini tidak mengklaim respons memiliki timing identik. GET/HEAD tracking dan struk memakai Cache-Control: no-store; tracking memakai Referrer-Policy: no-referrer dan X-Robots-Tag: noindex, nofollow.
- Tautan pelanggan — UI membuat /tracking.html#TOKEN; fragment tidak dikirim dalam permintaan halaman statis, lalu dibersihkan dari address bar oleh JavaScript. Token tidak masuk localStorage/sessionStorage; fetch tracking tanpa cookie. Token tetap rahasia bagi siapa pun yang menerima tautan; fragment bukan perlindungan dari penerima, riwayat browser sebelum script berjalan, extension, atau perangkat bersama.

## Operasional — Tindakan — Hasil

- HTTPS dan perangkat — gunakan origin HTTPS terkonfigurasi saat operasional. Staf membagikan tautan hanya kepada pelanggan terkait, bukan tautan struk internal; tutup halaman dan logout pada perangkat bersama. Jika tautan salah kirim, rotasi lalu bagikan ulang.
- Access log/cache — endpoint kompatibilitas GET /api/tracking/{token} tetap membawa token di path permintaan API. Sebelum deployment, operator wajib mengecualikan/redaksi token pada log reverse proxy, Cloudflare, tracing, analytics, dan pelaporan error; jangan log raw URI/query/request body/respons berisi token atau PII. Bypass cache untuk /api/*; jangan menganggap no-store aplikasi otomatis mengatur seluruh layanan eksternal. Repository belum berisi konfigurasi proxy/Tunnel produksi yang telah diverifikasi.
- Retensi — expiry membatasi akses publik, bukan menghapus transaksi atau profil. Tidak ada purge otomatis pelanggan/order/audit/backup pada perubahan ini. Owner perlu menetapkan jadwal retensi sesuai kebutuhan bisnis dan kewajiban yang berlaku; hindari menyimpan alamat/catatan yang tidak lagi diperlukan. Perubahan histori keuangan memerlukan rancangan tersendiri.
- Hak database — runtime membutuhkan SELECT/INSERT/UPDATE customers dan order_tracking_tokens serta UPDATE version orders, tanpa DDL/superuser. Migrator terpisah menjalankan 000007. Backup dapat berisi PII dan hash: batasi akses dan jangan commit ke Git.
- Rollback — hentikan writer saat upgrade dan verifikasi backup/restore salinan. Gunakan binary yang kompatibel dengan schema 7; binary schema 6 tidak memasok expires_at dan tidak menegakkan expiry. Jangan drop kolom, audit action, atau mengaktifkan kembali jalur tracking berdasarkan ID untuk downgrade. Utamakan forward fix; down migration otomatis tidak disediakan karena dapat menghilangkan data profil atau kebijakan akses publik.

## Verifikasi — Hasil

- Domain/platform — validasi canonical token, kebijakan 90 hari, normalisasi/edit data opsional, 4.096 token dari crypto/rand berukuran 256 bit tanpa duplikat pada sampel; sampling bukan bukti matematis entropy.
- Repository/service PostgreSQL — constraint hash/uniqueness, batas expiry, upgrade 6→7, pencarian literal/normalisasi kontak, version conflict, snapshot dan rollback audit, collision serta dua rotasi bersamaan diuji pada DB disposable.
- HTTP/UI — empat field publik secara exact, generic invalid/missing 404, authorization GET/HEAD struk/customer, CSRF rotasi, search/update/history boundary, escaping struk, safe DOM dan fragment diuji. Lihat [laporan hari 11](progress/day-11.md) untuk command dan batas verifikasi aktual.
